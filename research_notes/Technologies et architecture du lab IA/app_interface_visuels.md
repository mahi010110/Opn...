## 1. Framework desktop (Tauri 2 vs Electron, Wails, Flutter, Slint, egui) et découpage UI/backend des apps lourdes

### Takeaway
Tauri 2 (2.12.x, branche stable depuis octobre 2024) reste le meilleur choix pour un étudiant qui connaît Rust : sidecars pour embarquer des binaires d'appoint (QEMU, etc.), Channels IPC ordonnés pour streamer terminaux et paquets, updater signé gratuit, installeurs 5 à 28 fois plus légers qu'Electron selon les mesures. Le maillon faible est Linux (WebKitGTK : WebRTC désactivé par défaut, fenêtres blanches avec certains GPU NVIDIA). Tauri 3 (alpha depuis le 13/09/2026) prépare un runtime Chromium (CEF) optionnel mais n'est pas utilisable en production. Toutes les apps de référence (GNS3, Rancher Desktop, UTM, Docker Desktop, Podman Desktop) séparent une UI d'un moteur qui pilote VMs et conteneurs, souvent hors processus.

**Tauri 2 — pièges Linux**
- WebRTC est désactivé dans la compilation par défaut de WebKitGTK ; l'équipe de Hopp (app Tauri) l'a découvert tard et cela a bloqué sa version Linux — [Hopp, « hate webkit »](https://gethopp.app/blog/hate-webkit), [WebKit bug 274711](https://bugs.webkit.org/show_bug.cgi?id=274711), [discussion Tauri #8426](https://github.com/tauri-apps/tauri/discussions/8426).

**Tauri 2 — taille, IPC, sidecars, plugins**
- Benchmark Hopp (app à 6 fenêtres) : 8,6 MiB (Tauri) contre 244 MiB (Electron), ~172 Mo contre ~409 Mo de RAM — [dev.to/gethopp](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4) ; Better Stack mesure 57 Mo contre 323 Mo et rappelle que Tauri tourne sur trois moteurs web différents selon l'OS — [Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/).
- IPC : le système d'événements Tauri n'est pas conçu pour la faible latence ni le haut débit ; les **Channels** sont rapides, livrent des données ordonnées et servent en interne à la sortie des processus enfants et aux messages WebSocket — [Tauri, Calling the Frontend from Rust](https://v2.tauri.app/develop/calling-frontend/). Conseil communautaire : envoyer du binaire (`Vec<u8>` → `Uint8Array`) plutôt que de gros tableaux JSON — [catalogue tauri-events-channels](https://stuffbucket.github.io/skills/catalog/tauri-events-channels-streaming/).
- Sidecars : chaque entrée `bundle.externalBin` doit exister avec le suffixe `-$TARGET_TRIPLE` (ex. `my-sidecar-aarch64-apple-darwin`) ; appel JS `Command.sidecar('binaries/my-sidecar')` (plugin shell), appel Rust `.sidecar("my-sidecar")` — [Tauri, Embedding External Binaries](https://v2.tauri.app/develop/sidecar). L'exécution exige une capability du plugin shell avec `"sidecar": true` (source tierce) — [catalogue tauri-sidecar](https://stuffbucket.github.io/skills/catalog/tauri-sidecar/). `tauri-plugin-shell` 2.6.0 (2026-10-28) — [crates.io](https://crates.io/crates/tauri-plugin-shell).
- Plugins officiels publiés en oct.–nov. 2026 : updater 2.14.1, sql 2.6.0, store 2.5.1, single-instance 2.5.5, log 2.10.2, autostart 2.7.0, websocket 2.5.0 — [tauri-plugin-updater](https://crates.io/crates/tauri-plugin-updater), [tauri-plugin-sql](https://crates.io/crates/tauri-plugin-sql), [tauri-plugin-store](https://crates.io/crates/tauri-plugin-store), [tauri-plugin-single-instance](https://crates.io/crates/tauri-plugin-single-instance), [tauri-plugin-log](https://crates.io/crates/tauri-plugin-log), [tauri-plugin-autostart](https://crates.io/crates/tauri-plugin-autostart), [tauri-plugin-websocket](https://crates.io/crates/tauri-plugin-websocket). **Comment les apps lourdes séparent UI et backend**
- GNS3 : GUI Qt ou web UI → **contrôleur** (unique, détient l'état du projet, API REST JSON, Swagger sur `/docs`, API déclarée non stable) → **compute** (lance QEMU, Docker…, local ou distant) ; gns3-gui et gns3-server 3.0.6 (2026-01-28) — [GNS3 architecture](https://docs.gns3.com/docs/using-gns3/design/architecture), [gns3-server docs](https://gns3-server.readthedocs.io/en/latest/general.html), [PyPI gns3-gui](https://pypi.org/project/gns3-gui/).
- Rancher Desktop : 1.x = application Electron qui enveloppe d'autres outils, avec Lima (macOS/Linux) et WSL2 (Windows) ; la 2.0 (préversion technique) sort le backend de la GUI dans un programme d'arrière-plan `rdd` qui utilise Lima partout, car un backend logé dans la GUI rendait des fonctions comme les snapshots difficiles — [history](https://docs.rancherdesktop.io/blog/history-of-rancher-desktop/), [welcome to Rancher Desktop 2](https://docs.rancherdesktop.io/blog/welcome-to-rancher-desktop-2/) ; une revue d'architecture (non officielle) décrit un plan de contrôle Go unique bâti sur la machinerie d'API Kubernetes — [architecture review, mars 2026](https://rancher-sandbox.github.io/rancher-desktop-2/20260321-architecture-review.md).
- Docker Desktop : le processus hôte `com.docker.backend` gère réseau et accès fichiers entre l'hôte et la VM Linux sur Windows/Mac, et tout le trafic sortant des conteneurs part de ce processus — [docs réseau Docker Desktop](https://docs.docker.com/desktop/features/networking/).
- UTM : backend indépendant de la plateforme (`Services/`, `Configuration/`) + frontend SwiftUI ; deux backends VM derrière un protocole commun (QEMU via QEMUKit/CocoaSpice, Virtualization.framework) ; sur macOS, QEMU tourne hors processus via XPC (QEMUHelper → QEMULauncher), avec des profils de provisioning séparés pour les entitlements hyperviseur — [AGENTS.md UTM](https://raw.githubusercontent.com/utmapp/UTM/HEAD/AGENTS.md).
- Podman Desktop : extensions isolées qui ne communiquent qu'au travers de l'API Podman Desktop, écrites en TS/JS et empaquetées en images OCI ; une extension a une partie backend et une partie frontend (webview) reliées par RPC/`postMessage` ; des extensions Docker Desktop tournent via un wrapper — [Podman Desktop extensions](https://podman-desktop.io/docs/extensions), [tutoriel extension](https://podman-desktop.io/tutorial/writing-custom-extensions).

### Inferences
- Pour un solo Rust qui vise Windows en premier : Tauri 2.12 stable, sans attendre Tauri 3. Sur Windows, WebView2 est basé sur Chromium, donc le risque de compatibilité est concentré sur Linux : tester tôt AppImage/deb sous NVIDIA et Wayland.
- Ne pas compter sur WebRTC dans la webview Linux : faire le P2P (héritage Open-Contact) côté Rust, par exemple avec `webrtc` (webrtc-rs, stable la plus haute 0.21.1, publication le 2026-11-07) ou `str0m` 0.25.0 (2026-11-03), et Nostr avec `nostr-sdk` 0.45.6 (MIT) — [crates.io webrtc](https://crates.io/crates/webrtc), [str0m](https://crates.io/crates/str0m), [nostr-sdk](https://crates.io/crates/nostr-sdk).
- Architecture à calquer sur GNS3 et Rancher Desktop 2 : un « moteur de lab » Rust (état, orchestration, capture, serveur MCP) séparé de l'UI par une frontière d'API (commandes + Channels). En V1 il peut tourner dans le processus Tauri (runtime tokio), mais cette frontière permettra de l'extraire plus tard en daemon/sidecar (privilèges réseau, VMs qui survivent à la fermeture de la fenêtre).
- Binaires lourds (QEMU, tcpdump/dumpcap, éventuellement Zeek) en sidecars `externalBin`, un binaire par triple cible. QEMU et Wireshark sont sous GPL : les distribuer comme programmes séparés, avec offre de sources — à valider juridiquement.
- Electron reste le plan B si Linux/WebKitGTK bloque (rendu Chromium identique sur les trois OS, au prix de ~200 Mo et de plus de RAM), ou Tauri 3 + CEF quand il sera stable. Wails v3 vient d'être stabilisé mais impose Go. Flutter, Slint et egui obligeraient à réécrire ce que xterm.js, noVNC, React Flow, Excalidraw et Wiregasm offrent déjà dans un webview : coût prohibitif pour ce projet.

## 2. Terminaux intégrés, consoles graphiques (VNC/SPICE/RDP), consoles série, enregistrement et rejeu

### Takeaway
La base standard est xterm.js 6 côté UI, alimenté côté Rust par un PTY (portable-pty, tauri-plugin-pty), une session SSH (russh) ou la console série/exec des machines du lab. Pour l'écran des VMs, le plus simple est noVNC branché directement sur le serveur VNC WebSocket intégré à QEMU (QEMU ≥ 5.0). Pour RDP « léger », IronRDP (Rust/WASM, MIT/Apache) est l'option moderne, mais il exige une passerelle RDCleanPath ; Guacamole est lourd (guacd en C + serveur Java ou Node) et spice-html5 est un prototype abandonné. Pour le rejeu : asciicast v3 (asciinema 3.0) pour les terminaux, rrweb pour l'UI, les enregistrements Guacamole si on l'utilise.

## 4. Tableau blanc et diagrammes dessinés par l'IA

### Takeaway
Excalidraw (MIT) est le choix sûr pour un tableau blanc où l'IA dessine : licence libre, conversion Mermaid → Excalidraw officielle, plusieurs serveurs MCP existants. tldraw 5.x est plus avancé côté agents (kit Agent sous MIT), mais son SDK exige une clé de licence en production (licence « hobby » gratuite, accordée au cas par cas, non commerciale et avec filigrane). Mermaid 12 (MIT) est le format intermédiaire le plus robuste pour un LLM (séquences, paquets, architecture), et les sorties structurées ou outils stricts garantissent un JSON valide.

### Cited Findings
- Excalidraw `@excalidraw/excalidraw` : dernière version stable 0.18.1 (2026-04-20, MIT), paquet mis à jour jusqu'au 2026-11-12 ; `@excalidraw/mermaid-to-excalidraw` 3.6.0 (2026-11-04, MIT) — [npm excalidraw](https://www.npmjs.com/package/@excalidraw/excalidraw), [npm mermaid-to-excalidraw](https://www.npmjs.com/package/@excalidraw/mermaid-to-excalidraw).
- Serveurs MCP Excalidraw : yctimlin/mcp_excalidraw = serveur de canevas (Excalidraw web) + serveur MCP, synchronisés en temps réel par WebSocket ; l'Excalidraw MCP officiel affiche les diagrammes dans le chat ; une variante valide du Mermaid puis le convertit en scène Excalidraw — [mcp_excalidraw](https://mcpservers.org/servers/yctimlin/mcp_excalidraw), [README mcp_excalidraw](https://cdn.jsdelivr.net/gh/yctimlin/mcp_excalidraw@main/README.md), [Excalidraw MCP (glama)](https://glama.ai/mcp/servers/pgqivr93mx).

### Inferences
- Pipeline conseillé : quand le contenu est structuré, l'IA produit du **Mermaid** (séquence, packet, flowchart, architecture), rendu tel quel ou converti en Excalidraw pour être annoté à main levée. Le streaming des entrées d'outil permet de commencer à dessiner avant la fin de la réponse.

- La licence tldraw « hobby » pourrait convenir à un projet étudiant gratuit, mais elle reste discrétionnaire, impose le filigrane, et tout usage commercial futur (centres de formation) demanderait une licence payante : Excalidraw est plus sûr.

### Gaps
- Pas trouvé d'exemple open source documenté d'« IA tuteur qui dessine pendant qu'elle explique », au-delà de tldraw Agent, Agent Draw et des MCP Excalidraw.
- Animation progressive des éléments via l'API Excalidraw non vérifiée (à prototyper).
- Grammaire complète de `architecture-beta` non vérifiée.

## 5. Capture de paquets et animations pédagogiques

### Takeaway
Capturer **dans** le lab (tcpdump/dumpcap dans les conteneurs ou VMs Linux, ou sur les bridges de l'hôte Linux du lab) évite Npcap sous Windows, dont la redistribution est payante. ### Takeaway
GitHub Releases + `tauri-action` couvrent tout gratuitement : NSIS/MSI, dmg, AppImage/deb/rpm, plus `latest.json` pour l'updater signé. Une signature Windows gratuite est possible via SignPath Foundation (projet sous licence OSI, builds automatisés) ; Azure Artifact Signing semble fermé aux particuliers français. Sans signature, SmartScreen affiche « application non reconnue », et même un certificat EV ne le contourne plus depuis 2024. Sur macOS, pas de notarisation sans 99 $/an : distribuer une build signée ad-hoc avec la procédure « Ouvrir quand même », et renoncer au tap Homebrew officiel (casks non conformes à Gatekeeper désactivés depuis le 1er septembre 2026). winget et Flathub restent gratuits, mais Flathub exige un build hors ligne depuis les sources.

### Cited Findings
- Cibles de bundle Tauri : NSIS (.exe), MSI (WiX), deb, rpm, AppImage, dmg/.app ; sous Windows, `tauri build` produit MSI + NSIS par défaut ; NSIS se cross-compile hors Windows (cargo-xwin), MSI demande un hôte Windows — [catalogue tauri-bundling](https://stuffbucket.github.io/skills/catalog/tauri-bundling/), [tauri-bundler, settings.rs](https://docs.rs/crate/tauri-bundler/2.9.0/source/src/bundle/settings.rs). tauri-bundler 2.10.0 ajoute `bundleVCRuntime` (DLL VC++ dans les installeurs MSI et NSIS) — [tauri-bundler 2.10.0](https://v2.tauri.app/release/tauri-bundler/v2.10.0/).

### Inferences
- Ordre de priorité : (1) GitHub Releases + tauri-action dès la première version (Windows NSIS, Linux AppImage + deb, macOS dmg ad-hoc) avec updater signé ; (2) candidature SignPath juste après la première release publique ; (3) manifeste winget ; (4) Flathub quand l'app sera stable ; (5) notarisation Apple seulement si un sponsor ou un budget apparaît.
- Documenter dans le README et sur la page de téléchargement, en FR et EN, les écrans SmartScreen (« Informations complémentaires → Exécuter quand même ») et Gatekeeper (« Ouvrir quand même »), avec captures.
- Les gros sidecars (QEMU, images de VMs) alourdissent installeurs et mises à jour : prévoir le téléchargement à la demande des composants lourds plutôt qu'un installeur monolithique (à valider avec la recherche sur la couche de virtualisation).

### Gaps
- Prix exact d'Azure Artifact Signing non récupéré ; éligibilité des particuliers hors USA/Canada à revérifier auprès de Microsoft.
- Pas de durée chiffrée pour acquérir une réputation SmartScreen.
- Comportement exact de macOS 26 avec des apps ad-hoc non notarisées non vérifié.
- Délais et critères actuels d'acceptation de SignPath non vérifiés (page de candidature non lue).

## 7. Questions transverses : stockage local, i18n, accessibilité, plugins, tests et CI

### Takeaway
SQLite côté Rust (rusqlite ou sqlx) comme source de vérité ; i18n FR/EN avec Paraglide JS ou i18next ; accessibilité héritée du webview, à préserver (ne pas capturer Tab ni les flèches), React Flow et xterm.js ayant des modes clavier et lecteur d'écran. Pour les plugins : content packs déclaratifs + connecteurs via MCP, et WASM (Extism) seulement si du code tiers doit tourner dans un bac à sable. CI gratuite sur GitHub Actions pour un dépôt public ; KVM fonctionne sur les runners Linux hébergés sans support officiel, jamais sur macOS, et la virtualisation imbriquée n'est pas fiable sur Windows.

Extism plus tard si des contributeurs doivent ajouter des vérificateurs exécutables.
- CI : matrice windows/macos/ubuntu pour build, tests unitaires et E2E WebdriverIO ; tests d'intégration du moteur de lab (QEMU/KVM, conteneurs) uniquement sur ubuntu-latest, en acceptant que KVM n'y soit pas garanti.

- Statut actuel de la virtualisation imbriquée sur `windows-latest` non confirmé (sources anciennes).

- Bibliothèques de mise en page à panneaux ancrables (pour l'écran Lab) non étudiées.

## 8. Synthèse : pile recommandée pour une première version (V1)

### Takeaway
Pile V1 réaliste pour un solo d'ici l'examen de juillet 2027 : Tauri 2.12 (Rust) + React/TypeScript ; un moteur de lab Rust exposé en commandes/Channels et en serveur MCP ; React Flow + ELK pour la topologie vivante ; xterm.js 6 + noVNC (VNC WebSocket de QEMU) pour les consoles ; etherparse + Wiregasm pour les paquets, avec une Event List à la Packet Tracer ; Excalidraw + Mermaid pour le tableau blanc de l'IA ; SQLite (rusqlite) ; asciicast v3 + journal d'événements pour le rejeu ; distribution via GitHub Releases + SignPath + winget, macOS en ad-hoc.

### Cited Findings
- Tauri 2 est stable (2.12.5) alors que Tauri 3 est en alpha (3.0.0-alpha.6) — [crates.io tauri](https://crates.io/crates/tauri) ; les Channels sont conçus pour des flux ordonnés à haut débit — [Tauri, Calling the Frontend](https://v2.tauri.app/develop/calling-frontend/).

- noVNC se connecte directement au VNC WebSocket de QEMU ≥ 5.0 — [Launchpad, bug 1849644](https://bugs.launchpad.net/qemu/+bug/1849644).
- Excalidraw est sous MIT, tldraw exige une clé de licence en production — [npm excalidraw](https://www.npmjs.com/package/@excalidraw/excalidraw), [tldraw, license key](https://tldraw.dev/sdk-features/license-key).
- Wiregasm est sous GPL-2.0-or-later, asciinema (crate) sous GPL-3.0-or-later, elkjs sous EPL-2.0 OR GPL-3.0-or-later, noVNC sous MPL-2.0 — [GitHub wiregasm](https://github.com/good-tools/wiregasm), [crates.io asciinema](https://crates.io/crates/asciinema), [npm elkjs](https://www.npmjs.com/package/elkjs), [npm @novnc/novnc](https://www.npmjs.com/package/@novnc/novnc).

- Licence de l'app : choisir dès le départ une licence compatible avec les composants copyleft que l'on veut intégrer (par exemple GPL-3.0-or-later, qui accepte Wiregasm en GPL-2.0-or-later, elkjs via son option GPL-3.0, noVNC en MPL-2.0 et les dépendances MIT/Apache-2.0), et livrer QEMU et les outils Wireshark comme programmes séparés avec leurs sources : à faire valider.
- Principaux risques : (1) Linux/WebKitGTK (rendu, WebRTC) → tester tôt, plan B Electron ; (2) poids des sidecars et des images de VMs → téléchargements à la demande ; (3) charge cumulée dans un seul webview (xterm.js WebGL + React Flow + Excalidraw + Wiregasm) → prototype de performance avant d'aller plus loin ; (4) dépendance au mode « Ouvrir quand même » sur macOS sans notarisation.
- Ordre de construction conseillé : moteur de lab + topologie vivante + terminaux (le cœur de l'écran Lab), puis événements paquets + Event List, puis IA (MCP + annotations + tableau blanc), puis rejeu, puis distribution signée.

### Gaps
- Aucun prototype n'a validé la performance cumulée des composants dans WebView2 et WebKitGTK.
- Le choix final dépend de la couche de virtualisation (QEMU/WHPX, WSL2, Hyper-V, conteneurs), couverte par d'autres recherches.
- Pas de retour d'expérience trouvé sur une app Tauri combinant QEMU en sidecar et noVNC.
